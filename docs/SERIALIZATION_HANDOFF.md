## Исправления после проверки преподавателем — 5 ноября 2026

- Общая логика выделена в `BaseLinearEngine`; Сугено и Мамдани — независимые наследники.
- Python `model_ref()` возвращает `ModelView`, а не сырой `IModel`.
  Сохранение через движок и представление сохраняет одинаковые метаданные.
- Загрузка читает модель и `extra.linear_api` из одного дерева JSON.
- Сохраняются имена и параметры всех зарегистрированных MF, включая неиспользуемые;
  `find_belonging()` работает после загрузки и повторного сохранения.
- Неизвестные типы проверяются в реестрах с осмысленной `invalid_argument`;
  глобальный перехват `bad_optional_access` удалён.
- `get_defuzzer()` сообщает фактический дефаззификатор после восстановления.
  Параметры интегратора Мамдани также восстанавливаются в состоянии фасада.

Проверки исправленной версии: **122 C++-теста**, **121 Python-тест**;
дополнительно **31 тест сериализации** на отдельной сборке wheel CPython 3.14
и **31 тест сериализации** на MSYS2 Python 3.14. `mkdocs build --strict` — успешно.

Первоначальный архив, описанный ниже, относится к версии до этих исправлений.
Для проверки исправленного кода используйте актуальные ветки `python-serialization`

## Что реализовано по списку

| Пункт | Python API |
|---|---|
| 1. Сохранение | `engine.save_to_string()`, `engine.save_to_file(path)`, `engine.to_dict()` |
| 2. Загрузка | `openfll.load_from_string(text)`, `openfll.load_from_file(path)` возвращают собранный движок |
| 3. Построенная модель | `engine.model_ref()` возвращает `openfll.ModelView` с `calculate()` и сериализаторами |
| 4. Mamdani | `openfll.MamdaniEngine` над `MamdaniBuilder` и `CentroidDefuzzer`; диапазон/шаг через `set_integrator(start, end, step)` |
| 5. Дефаззификатор | `set_defuzzer("wtaver"/"wtsum")` для Сугено; `"centroid"` для Мамдани |
| 6. Степень принадлежности | `engine.find_belonging(mf_name, value)` вызывает нативную MF |
| 7. Имена переменных | `get_input_var_names()`, `get_output_var_names()`, включая загруженные модели |

`IModel::pack(IWriterProvider&)` вызывается внутри сериализаторов. Сам низкоуровневый
интерфейс поставщика средств записи и цепочки вызовов построителей в Python не экспортируются.
Загрузка переводит `FuzzyModelBundle` в движок с теми же объектами переменных,
которые использует модель: `set_input()` действительно влияет на её вычисления.
Ссылка `model_ref()` удерживает своего владельца в памяти.

## Исправления, необходимые для совместимости

- Разрешены однотермовые антецеденты; обновлённое ядро ошибочно требовало оператор.
- `predict()` получает имена из C++ и работает на моделях, загруженных без ручной регистрации.
- Порядок регистрации переменных хранится в необязательном `extra.linear_api`.
- Для Мамдани сохраняются и восстанавливаются диапазон и шаг интегратора.
- Для отключённых консеквентов нескольких выходов используется индекс `-1`;
  порядок масок при загрузке приводится к фактическому порядку выходов нового контекста.
- Ошибочные индексы и размеры правил проверяются до обращения к C++-массивам.
- Пути с кириллицей/пробелами и `pathlib.Path` поддерживаются; файловые ошибки — `OSError`.
- Существующий C++-тест сериализации проверяет выходы модели по именам;
  раньше он сравнивал установленные входные значения и мог пропускать ошибки.
- Исправлена исходная ошибка структуры `pyproject.toml`, мешавшая сборке wheel.
- Добавлены типизация, документация, пример, закрепление исходного C++-коммита и патча в автоматической сборке.

## Установка передаваемого wheel

Файл: `openfll-0.3.0.dev1-cp314-cp314-mingw_x86_64_ucrt_gnu.whl`.
Платформа: Windows x64, MSYS2 UCRT64 Python 3.14. Проверено на Python 3.14.7,
GCC UCRT 16.2.0. Этот wheel не совместим с обычной сборкой Python с python.org;
для неё нужна отдельная нативная сборка.

Из каталога распакованного архива в PowerShell, при установленном MSYS2 UCRT64
с Python и NumPy:

```powershell
C:/msys64/ucrt64/bin/python.exe -m venv --system-site-packages .venv
./.venv/bin/python.exe -m pip install --no-deps ./openfll-0.3.0.dev1-cp314-cp314-mingw_x86_64_ucrt_gnu.whl
./.venv/bin/python.exe ./05_serialization_demo.py --output-dir demo_models
```

`--no-deps` предполагает, что NumPy установлен через MSYS2. Для запуска всех
тестов также нужны pytest, sklearn, matplotlib и openpyxl.

## Ограничения формата

Нативный JSON сохраняет структуру модели, но не текущие значения входов.
Загруженная модель уже собрана и не допускает `add_*`/повторный `build()`.
Метаданные `extra.linear_api` сохраняют имена и параметры всех зарегистрированных
MF, включая неиспользованные термы, поэтому `find_belonging()` работает после
загрузки. Старые JSON без этих метаданных не позволяют восстановить исходные
имена MF. Python-метаданные для `plot_mf()` автоматически не восстанавливаются.

JSON ядра без `extra.linear_api` поддерживается; порядок колонок в этом случае
следует уточнять через `get_input_var_names()` либо задавать `input_names` явно.
Для нескольких выходов используйте одиночный вызов `predict(..., output_name=...)`
или `set_input/calculate/get_output`; нативный пакетный расчёт поддерживает один выход.
Для Mamdani сейчас доступен centroid с одним общим диапазоном интегрирования.
